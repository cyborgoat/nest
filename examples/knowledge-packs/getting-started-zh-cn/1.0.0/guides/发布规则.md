# 知识包发布规则

遵循这些约定，可以让知识包在 Nest Desktop、Hub、macOS、Linux 和 Windows
之间稳定迁移与共享。

## 使用稳定的知识包标识

- 使用简短的小写英文 ID，例如 `engineering-handbook`。
- ID 只能包含小写英文字母、数字和单个连字符。
- ID 必须与知识包最外层文件夹名称一致。
- 首次发布后不要更改 ID。更改 ID 会被视为新的 Hub 项目，而不是原项目的新版本。
- 显示名称可以更易读，也可以使用空格和中文，例如“工程手册”。

## 清晰地命名内容文件

Markdown 文件名支持 Unicode，可以直接使用中文：

```text
engineering-handbook/
  开始阅读.md
  guides/
    发布流程.md
    故障排查.md
```

为了兼容 Windows：

- 不要使用 `< > : " / \ | ? *`。
- 文件名末尾不要使用空格或句点。
- 不要使用 `CON`、`NUL`、`PRN`、`AUX`、`COM1`、`LPT1` 等保留名称。
- 避免创建仅大小写不同的两个路径。
- 保留 `.md` 扩展名，并使用相对路径链接知识包内的文件。

`guides`、`concepts` 和 `images` 等文件夹名称只是约定，并非强制要求。可以根据
读者查找内容的方式组织文件。

## 将 `pack.json` 用作元数据

从文件夹导入时，不需要手动创建 `pack.json`。Nest 会根据文件夹生成合理的默认值，
让你检查后在安装副本中创建清单。

已安装、导出、通过 ZIP 导入和发布的知识包目前使用 `pack.json` 作为可移植清单：

```json
{
  "id": "engineering-handbook",
  "name": "工程手册",
  "description": "团队共享的工程实践。",
  "version": "1.2.0",
  "path": "engineering-handbook"
}
```

- `id` 是稳定的 Hub 标识，必须与知识包文件夹名称一致。
- `name` 是向用户显示的名称，可以使用中文。
- `description` 可选，但有助于用户判断是否需要安装。
- `version` 必须是语义化版本。
- 如果包含 `path`，其值必须与 `id` 相同；建议交给 Nest 管理。

优先通过 Nest 编辑元数据。重命名知识包或选择发布版本时，Nest 会同时更新清单和
本地记录。不要在 `pack.json` 中放入文档正文、密码、API 密钥或当前电脑的绝对路径。

## 统一管理版本

使用 `主版本.次版本.修订版本` 格式：

- 修订版本（`1.0.1`）：修正错误或进行小幅文字调整。
- 次版本（`1.1.0`）：增加新内容，同时保持原有结构和链接可用。
- 主版本（`2.0.0`）：大幅调整结构、破坏旧链接或显著改变使用方式。

每个 Hub 版本只能发布一次。在 Nest 的发布对话框中选择下一个版本；上传前，Nest
会把该版本写入导出的清单。

## 发布前检查

1. 在源代码管理中审查全部修改。
2. 使用渲染视图打开所有修改过的 Markdown 文件。
3. 检查相对链接、图片、标题和 `@` 引用示例。
4. 删除密码、个人数据、临时文件和当前电脑的专用路径。
5. 确认知识包 ID、显示名称、描述和目标版本。
6. 大幅调整目录结构后，先导出 ZIP 并重新导入测试。
7. 提交发布请求，并在消息中心关注审核结果和管理员意见。

ZIP 必须只包含一个顶层知识包文件夹、Nest 生成的 `pack.json`，以及至少一个
Markdown 文件。
